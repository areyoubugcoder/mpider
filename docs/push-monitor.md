# 推送监测

在 Windows 上保持微信登录，从左侧进入“推送监测”，选择范围与频率后开启。程序只读扫描微信进程中存在的文章链接，持久化候选，再获取文章网页核对公众号、标题和发布时间。符合条件的文章自动加入现有文章库；下载正文和导出仍使用文章库的入口。

## 与主页识别的区别

| 操作 | 用途 | 是否自动新增文章 |
| --- | --- | --- |
| 推送监测 | 后台发现本机微信内存中的文章链接 | 是，通过网页身份和时间窗校验后入库 |
| 主页识别 | 开启后手动打开公众号主页，登记公众号和采集会话 | 否 |
| 同步最新文章 | 对已登记公众号显式获取首页列表 | 是 |

推送监测与主页识别可以同时开启，开关相互独立。文章按 `biz + mid + idx` 去重，监测不会改写已有历史游标或采集会话；监测新建的公众号仍需主页识别才能执行列表翻页。

## 时间、范围和请求

- 默认每轮扫描结束后等待 10 秒；扫描本身和网页处理也需要时间，不承诺固定送达延迟。
- 默认处理在首次发现前 24 小时内发布的文章，可设置 1～168 小时。首次开启也会处理内存中已有的近期链接，记录可能包含用户打开的旧文章。
- “发现时间”表示软件观察到链接的时间，不是微信推送送达时间。
- 可以监测全部公众号，或按已登记公众号的稳定标识选择范围。短链需先解析网页才能知道所属公众号，可能占用一次请求额度后被过滤。
- 默认每小时最多 60 次网页请求，最多设置 120 次。滚动额度跨停止、重启保留，失败请求同样计数。
- 网页请求与正文下载共享正文请求间隔和全局冷却，不消耗列表翻页预算。请求前先记账，不自动跟随重定向；网络失败等最多处理三次。网页要求验证或返回 429 时进入两小时全局冷却，内存扫描继续。
- 新发现的候选优先于旧积压和失败重试。待处理候选上限 10,000；达到上限后保留当前队列，其余链接在后续仍存在于内存时重新发现。终态监测记录在开启时及每 30 轮扫描清理超过 30 天的部分；文章不随监测记录清理。

停止监测会取消正在等待的网页响应，不接受晚到结果。应用重启后监测保持关闭，需要手动重新开启；未完成候选继续排队，不会被吸收为已完成基线。删除公众号或文章后，删除前已发现的迟到结果不会将其重建。

## 支持范围

当前实现面向 64 位 Windows 微信的 `Weixin.exe`、`WeChat.exe`、`WeChatAppEx.exe`。主进程每轮扫描，内嵌浏览器按热点及每 30 轮全量兜底扫描。支持 ASCII 与 UTF-16LE 链接，读取已提交的可写、非代码映像内存区。不注入、不操作微信窗口、不加载第三方监控 EXE。

只有进入可扫描内存且保留足够久的链接才能被发现。微信退出、URL 释放、内存布局变化、权限不一致或网页不可访问都可能影响结果；不能用它保证完整补齐离线期间的推送或代替历史翻页。macOS 可以查看记录，但不能开启此监测。

## 本地诊断

需要自行准备 Windows Rust 构建环境。以下命令会读取已登录微信的进程内存；第二条还会按配置请求文章网页，请只在明确授权的测试环境运行。

```powershell
cargo run --locked -p mpider-core --example push_monitor -- scan
cargo run --locked -p mpider-core --example push_monitor -- run .\push-test.db 120 10
```

`run` 必须显式提供独立数据库、运行秒数和每小时请求上限。终端只输出汇总计数，完整文章信息保存在指定数据库。手动触发 `CI` workflow 可取得诊断程序与桌面开发程序，产物仅用于验收，不作为正式发布或更新包。

## 本地接口约定

Tauri 提供 `workbench_push_status`、`workbench_push_start({config})` 和 `workbench_push_stop`。配置包含 `scan_seconds`（5～300）、`recent_hours`（1～168）、`hourly_budget`（1～120）和 `bizzes`（空集合表示全部）。正在运行时不能重复开启；先停止再调整设置。状态返回平台支持性、运行状态、队列和入库计数、近一小时请求数及最近 100 条记录，不返回内存片段或候选原始 URL。

离线回归使用虚构页面和本机 HTTP 服务，覆盖身份不匹配、跨号去重、原子入库、停止期间取消、重启恢复、删除屏障、额度与验证页冷却。它们验证程序行为；实际微信版本上的发现能力还需要单独实机验收。
