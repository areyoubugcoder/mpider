# 推送监测

从左侧进入“推送监测”，分别控制新链接扫描和已保存链接处理：

- “开启推送监测”：在 Windows 上只读扫描已登录微信的进程，持续发现并保存新链接。仅开启监测不会请求文章网页。
- “开始处理”：独立处理已经保存的链接，获取文章网页核对公众号、标题和发布时间。无需开启监测或保持微信运行；符合条件的文章自动加入文章库。队列清空后保持等待，后续追加的链接也会自动处理。

两个功能可以同时开启，也可以单独使用。下载文章和导出仍使用文章库的入口。

## 与主页识别的区别

| 操作 | 用途 | 是否自动新增文章 |
| --- | --- | --- |
| 推送监测 | 后台发现本机微信内存中的文章链接 | 否，保存到待处理队列 |
| 处理待处理链接 | 解析已保存链接并校验身份和时间窗 | 是 |
| 主页识别 | 开启后手动打开公众号主页，登记公众号和采集会话 | 否 |
| 同步最新文章 | 对已登记公众号显式获取首页列表 | 是 |

推送监测与主页识别可以同时开启，开关相互独立。文章按 `biz + mid + idx` 去重，监测不会改写已有历史游标或采集会话；监测新建的公众号仍需主页识别才能执行列表翻页。

## 时间、范围和请求

- 默认每轮扫描结束后等待 10 秒；扫描本身和网页处理也需要时间，不承诺固定送达延迟。
- 默认处理在首次发现前 24 小时内发布的文章，可设置 1～168 小时。首次开启监测也会发现内存中已有的近期链接，记录可能包含用户打开的旧文章。
- “发现时间”表示软件观察到链接的时间，不是微信推送送达时间。
- 可以监测全部公众号，或按已登记公众号的稳定标识选择范围；支持按名称或 ID 模糊搜索，搜索及加载更多时保留已有选择。短链需先解析网页才能知道所属公众号，可能占用一次请求额度后被过滤。
- 文章请求的间隔、重试和近 24 小时预算统一在“限流配置 → 文章下载”调整。推送页不再提供独立网页间隔或每小时上限。新配置默认文章下载间隔 1 秒、近 24 小时预算 86,400 次；已保存间隔保持原值，旧配置缺少文章预算时补入初始值。滚动额度跨停止、重启保留，跳转、失败和重试同样计数。
- 推送解析与文章下载共享请求工作位和文章预算，每个工作位在网页响应结束后等待配置间隔，列表预算独立计算；图片仅受图片间隔控制，不消耗文章预算。推送解析仍不延长全局冷却。请求前先记账，跳转只接受规范微信文章地址并逐跳重新申请许可；每个候选最多发送首次请求加配置的额外重试次数（包含跳转和失败）；默认合计三次。网页要求验证、返回 429 或网络失败时，候选等待 1 秒后可重试（仍受文章下载间隔和预算限制），不会跟随验证页或自动完成验证。扫描与网页解析并行，已有队列不必等待内存扫描结束。
- 新发现的候选优先于旧积压和失败重试。待处理候选上限 10,000；达到上限后保留当前队列，其余链接在后续仍存在于内存时重新发现。终态监测记录在开启时及每 30 轮扫描清理超过 30 天的部分；文章不随监测记录清理。

“最近发现”只展示首次发现时间在最近一小时内的记录，首次只加载 20 条，点击一次“加载更多”才再读取下一批 20 条，重新进入页面从首批开始；不再固定截断为 100 条。已过期记录不会因后来解析完成而重新出现在列表中，后台候选与文章不受这一展示窗口影响。

停止监测只停止扫描新链接，已开启的队列处理继续运行；“暂停处理”只取消正在等待的网页响应、保留未完成链接，不影响扫描。重新开始处理会继续已有队列，暂停前的晚到结果不会写入。应用重启后两个功能均保持关闭，可按需分别开启；未完成链接、请求次数和预算均保留。每条链接使用发现时保存的公众号范围与时间窗，之后修改监测设置不影响已有链接。删除公众号或文章后，删除前已发现的迟到结果不会将其重建。

## 支持范围

当前实现面向 64 位 Windows 微信的 `Weixin.exe`、`WeChat.exe`、`WeChatAppEx.exe`。主进程每轮扫描，内嵌浏览器按热点及每 30 轮全量兜底扫描。支持 ASCII 与 UTF-16LE 链接，长链保留 `sn` 及 16～256 位十六进制 `chksm`，不会将合法的较长签名丢弃；同一文章补齐签名后，失败候选在剩余次数内重新排队。读取已提交的可写、非代码映像内存区。不注入、不操作微信窗口、不加载第三方监控 EXE。

只有进入可扫描内存且保留足够久的链接才能被发现。微信退出、URL 释放、内存布局变化、权限不一致或网页不可访问都可能影响结果；不能用它保证完整补齐离线期间的推送或代替历史翻页。macOS 可以查看记录并处理已保存链接，但不能扫描微信进程。

## 本地诊断

需要自行准备 Windows Rust 构建环境。以下命令会读取已登录微信的进程内存；第二条还会按配置请求文章网页，请只在明确授权的测试环境运行。

```powershell
cargo run --locked -p mpider-core --example push_monitor -- scan
cargo run --locked -p mpider-core --example push_monitor -- run .\push-test.db 120 10
```

`run` 必须显式提供独立数据库、运行秒数和近24小时文章下载预算。终端只输出汇总计数，完整文章信息保存在指定数据库。手动触发 `CI` workflow 可取得诊断程序与桌面开发程序，产物仅用于验收，不作为正式发布或更新包。

## 本地接口约定

Tauri 提供以下本地命令：

| 命令 | 行为 |
| --- | --- |
| `workbench_push_status` | 返回 `run`（扫描状态）、`run.queue`（独立处理状态）及队列、入库、请求预算计数 |
| `workbench_push_events({before, limit})` | 分页读取最近发现记录 |
| `workbench_push_start({config})` / `workbench_push_stop` | 仅开启／停止 Windows 新链接扫描 |
| `workbench_push_queue_start` / `workbench_push_queue_stop` | 独立开启／暂停已保存链接处理，不要求 Windows 或微信进程；开启返回处理运行编号 |

`run.queue` 包含 `id`、`active`、`phase`、`next_fetch_at`、`reason`；请求等待时间和原因属于处理队列，不再覆盖扫描状态。两种运行分别防止重复开启、拒绝各自停止或重启前的晚到结果。已有数据库升级时保留候选、重试次数和升级前保存的筛选范围。

监测配置只包含 `scan_seconds`（5～300）、`recent_hours`（1～168）和 `bizzes`（空集合表示全部）；旧版独立请求间隔及每小时上限字段被忽略。文章预算使用限流策略中的 `body_daily_budget`（正整数），请求工作位数量使用 `body_workers`，每个工作位在网页响应结束后按 `body_gap_ms` 等待；首个请求立即发送，与文章下载共享工作位和预算。监测运行时先停止扫描再调整监测设置；期间可以继续处理已有链接。状态返回平台支持性、运行状态、队列和入库计数、共享的近24小时文章请求数及预算；状态接口不读取发现列表，发现记录仅在分页接口按批次读取，不返回内存片段或候选原始 URL。

发现记录分页按 `(first_seen_at, id)` 降序游标继续，`before` 传上一页的 `next_cursor`；末页返回空游标。`limit` 为 1～100，服务端每次读取均限制在最近一小时。状态与分页均不返回候选原始 URL。

离线回归使用虚构页面和本机 HTTP 服务，覆盖扫描与处理独立开关、关闭扫描后的独立 HTTP 处理、旧队列迁移、身份不匹配、跨号去重、原子入库、停止期间取消、重启恢复、删除屏障、共享文章间隔、24小时预算、最近一小时游标分页及验证页短暂重试。它们验证程序行为；实际微信版本上的发现能力还需要单独实机验收。
