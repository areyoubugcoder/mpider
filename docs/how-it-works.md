# 实现原理

> 一句话：本机装一张自己的 HTTPS 根证书 + 开本地代理，**只解密微信内置浏览器发往 `mp.weixin.qq.com` 的请求**，
> 从里面取到当前登录微信的会话凭证（`key` / `pass_ticket` …），再用普通 HTTP 客户端直连微信服务器回放
> 公众号接口翻文章列表、抓正文。抓凭证走代理，采集不走代理。

## 1. 为什么装证书 + 开代理就能抓到

微信 PC 端有两条完全不同的网络通道，本项目只碰第二条：

| 通道 | 谁在用 | 加密方式 | 能否解密 |
|---|---|---|---|
| ① 微信主协议 | 聊天、同步、心跳 | 腾讯私有 mmtls + 证书固定 | 解不开，强行拦截会弄断微信 |
| ② 内置浏览器 | 打开公众号文章的那个窗口 | 标准 HTTPS，信任系统根证书，无证书固定 | 能解密 |

公众号文章走通道②，它本质是一个普通 Chromium 内核的 WebView。只要它信任我们的根证书，本地中间人代理就能把它的 HTTPS 解成明文。

## 2. 拦截哪些 HTTPS

代理按 TLS 握手时的 SNI 分两类处理（`crates/core/src/capture.rs`）：

- **解密**：只有 `mp.weixin.qq.com`。从它的请求 URL / Cookie 里取凭证。
- **直通**：微信主协议域名（`*short.weixin.qq.com`、`*long.weixin.qq.com`、`dns.weixin.qq.com`、`mmtls.weixin.qq.com` …）在握手阶段原样透传，不解密、不改动。判定见 `probe.rs` 的 `is_wechat_pinned_host`，它显式排除 `mp.weixin.qq.com`。首次遇到没预料到的固定证书主机会握手失败一次，之后自动记住并放行。

其余顺带路过的域名（`res.wx.qq.com` 静态资源、`mmbiz.qpic.cn` 图片等）技术上也能解密，但不关心、不处理。

## 3. 凭证是什么、从哪来

在 PC 微信里打开一篇公众号文章时，那条 `GET /s?__biz=…&mid=…&idx=…&sn=…` 请求以及文章页脚本发出的
`getappmsgext` 请求里，带着当前登录微信的凭证：

```
__biz         公众号 ID
uin           微信用户 ID：一个微信号一个，换号才变
key           会话密钥：约 30 分钟过期，一个公众号一个，最关键
pass_ticket   会话票据：约 1 小时
appmsg_token / wxtoken / x5   其它辅助票据
```

代理层（`proxy_addon.rs`）把它们抠出来存进 SQLite 的 `credentials` 表。`key` 算不出来，只能等微信在内置浏览器里再发一次被截到；过期了就要再打开一次该号的文章。

## 4. 让微信自动打开文章：种子链接与接力

手动在微信里点文章不可持续，所以有一条自动化链路：

1. 用户把一条固定的**种子链接** `http://127.0.0.1:8787/` 发进微信「文件传输助手」，并在 App 里「框选」它在聊天窗口中的位置（`rpa.rs`，标定按微信号缓存）。
2. 每批任务开始时，App 起本地 MITM 代理与系统代理，RPA 模拟点击种子链接，微信内置浏览器打开它。
3. 种子链接指向 App 自己起的 HTTP 服务（`seedserver.rs`）。它只对微信 UA 的主文档请求输出一个页面，页面里的脚本把 `location.href` 跳到本批第一条文章链接。
4. 文章页经代理时被注入**接力脚本**（`relay.rs`）：停留一小段随机时间后跳到下一条链接，直到本批链接全部打开。每打开一条，代理就截到该公众号的新鲜凭证。
5. 编排器（`orchestrator.rs`）用看门狗盯着请求心跳：点空就重点，停滞就把在途链接放回队尾再重拉，命中验证页整批中止。

Chromium 内核对回环地址默认绕过系统代理，所以种子页请求根本不经代理，入口逻辑只能放在本机服务里，而不是靠代理注入。

**macOS 是人工模式**（`rpa.rs` 的 `MacWeChatController`，`WeChatController::manual()` 为真）：不枚举窗口、不模拟点击。每批开始时编排器照样起代理，然后推一条全局提醒（`runstate::alert_push("manual_open")`）让用户在微信内置浏览器打开任意一篇公众号文章——第 4 步的接力注入不要求是种子页，打开一篇就能自动接力本批其余链接并抓到凭证。等待上限抬到 `rpa::MANUAL_WAIT_SECS`（10 分钟）下限，凭证到位即返回并收掉提醒；集中续期同理。看门狗只在自动点击成功时工作，人工模式下不重点。GUI 按 `system_status.rpa_auto` 整体隐藏种子链接 / 框选 / 自检 / 测试点击等 Windows 专属 UI。

**待命页自轮询**（`seedserver.rs`，人工模式专用，`seedserver::set_resident_mode` 打开）让人只需操作第一批：种子页空闲时不再是纯说明页，而是一张「待命页」，用 `fetch` 链长轮询 `/wait`（服务端最多挂 20 秒，队列一有任务就返回首条；用 `fetch` 续接而不用 `setTimeout`，因为 Chromium 对后台页定时器节流到分钟级，promise 续接不受影响），拿到链接即跳走；MITM 注入的接力脚本在本批末条停留后 `location.replace` 回到种子页（`CaptureConfig.resident_home`），浏览器于是又回到待命。编排与续期在人工模式下先看 `seedserver::resident_alive()`（最近 45 秒内有过微信 UA 的长轮询）：在线就不推提醒、不抬等待上限，本批交给待命页；不在线才推「请打开一篇文章」。种子页在回环地址上，内置浏览器直连不经代理，所以批次之间代理停掉也不影响待命。Windows 自动点击模式不开这个开关：空闲种子页仍是说明页、末条不回落，避免上一批没关掉的窗口与新点开的种子页抢同一批队列。

## 5. 抓到凭证之后：直连回放

有了 `__biz + uin + key + pass_ticket`，采集就不需要微信、也不走代理（`collector.rs` / `wechat.rs`）：

```
列表：GET /mp/profile_ext?action=getmsg&__biz&uin&key&pass_ticket&offset=0   → JSON general_msg_list
      按响应里的 next_offset 翻页，直到出现早于「最后发布时间」的文章，或 offset 不再前进 / 空列表
正文：GET /s?__biz&mid&idx&sn                                                → 公开页，不需要 key
      交给 crates/article-md 转 Markdown（detail.rs，可多线程）
```

`can_msg_continue` 字段不可靠，真机首页就返回 0 但 `offset` 仍前进，翻到底只看 `next_offset`。
`ret=-3` 表示凭证过期，编排器把过期的号集中起来再接力一次续期（`credrefresh.rs`），然后从中断的 offset 续采。

**静默空页 —— 2026-09-10 起本节所述的列表采集已不可用**（`wechat::is_silent_empty_list`）：响应 HTTP 200、
`ret=0`、`errmsg="ok"`，却**没有列表容器**（顶层 `list` 数组或 `general_msg_list` 里的 `list`）且 `msg_count=0`，
`next_offset` / `real_type` 字段一并消失 —— 微信既不报错也不给数据。09-10 中午同一微信号还能正常采到 149 篇
（`general_msg_list` 22533 字节），当天下午起同一请求只剩空响应；随后用三个微信号（含一个**从未触发过限制、
本次是其首次列表请求**的全新号）、Windows 与 mac 两台机器、7 个公众号交叉验证，响应完全一致。全新号首次请求即空，
排除账号级限制，指向**服务端对该接口的调整**。

判定只在**首采首页**（`offset=0` 的第 1 页）进行：有文章的公众号首页不可能为空，真正翻到底至少在第 2 页或续采上，
不会误命中。命中即 `CollectOutcome.suspect_blocked`、`list_call_log.outcome="empty_suspect"`、warn 级日志 + 一条预警，
如实说明接口取不到数据而不是「没有更多历史」；不改变退避与上报行为。抓凭证、接力、正文解析等其余环节不受影响。

## 6. 限流与节奏

- `getmsg` 的限流**按微信号计**。`ret=-6` 表示该微信号被识别为异常，约一天后恢复，与 `__biz`、`key`、出口 IP 都无关，换 key 无用，换号即恢复。实测它是按 `uin` 累计约 200 次 / 24 小时的配额。
- 所以每次 `getmsg` 都过一道进程级闸门（`runstate.rs`，默认 8 到 20 秒随机间隔），每个微信号 24 小时预算默认 180 次，批次之间再间隔 60 秒。
- 正文 `/s` 是匿名直连，命中验证页多半是无效 `sn` 的坏链，先抓一条已知有效的对照链接确认，对照也是验证页才判限流停批。
- 429 / 5xx / 接口回网页视为 IP 级限流，整机退避 5 分钟起翻倍、封顶 1 小时；`ret=-6` 视为封号，按微信号记退避。退避状态持久化，重启不清零。
- 每次真实发出的 `getmsg` 都写 `list_call_log`（只记标量，不含 URL 与凭证），GUI「限流分析」页据此统计。

## 7. 添加公众号、定时巡检与历史抓取

**添加公众号不开微信。**「批量添加」只收文章短链（`/s/<id>`）：软件用桌面浏览器 UA 匿名直连文章页，页面脚本里就有
`var biz`、`var nickname`、头像与 `var item_show_type`（0 = 图文），读出来即建号（`addlink.rs`），并把这条短链记成该号的
**种子链接**（`accounts.seed_url`）。实测长链缺 `chksm` 参数时匿名访问必回验证页，所以只收短链；非图文文章一并拒绝。

**定时巡检**由控制面板「开始巡检」拉起（默认不开、不跨重启）：库里的公众号按轮自更新最新文章列表（`sweep.rs`），一批取
若干个本轮没查过的号，每号取最新一篇长链做接力取样（库里还没有文章的新号就用种子短链），`accounts.last_published_at`
做翻页依据；一轮跑完停留一段时间再来；轮状态持久化。取样链接打不开（验证页 / 已删除 / 隐私）就换次新一篇再接力，
最多换 3 次。「停止巡检」在当前批次结束后生效。

**历史抓取**（`history.rs`）对单个号往旧翻页，一页一个执行单元，由同一个主循环推进（历史模式）。巡检与历史抓取
**同一时刻只能跑一个**：巡检开着（含停止收尾中）时不能开始 / 继续历史任务，有历史任务（进行中或暂停）时不能开始巡检，
两端都在后端硬拦。应用重启时未完成的历史任务转为暂停，由用户点「继续」恢复，不会一启动就抢微信窗口。

## 8. 整体数据流

```
微信内置浏览器 ──打开文章──▶ 本地 MITM 代理（hudsucker + rcgen 自签 CA）
   通道② HTTPS                    │ 只解密 mp.weixin.qq.com，抠凭证 → credentials 表
   通道① mmtls ──按 SNI 直通──▶   │ 不碰，保微信不断线
                                  ▼
                      凭证池（key ≈ 30 分钟）
                                  │
                                  ▼
             回放采集器（reqwest 直连，不经代理）
                ├─ 列表：getmsg 翻页 → articles 表
                ├─ 正文：/s 公开页 → article-md → Markdown
                └─ 添加公众号：/s/<id> 短链公开页 → biz / 名称 → accounts 表（种子链接）
                                  │
                                  ▼
             SQLite ──▶ GUI 浏览 / 导出 / 可选 POST 到用户自己的上报服务
```

## 9. 必然的约束

- 装的是全机根证书、切的是系统代理，用完 App 会自动复位（`SystemProxyGuard`）。守卫另有两道兜底：Tauri 退出事件调 `sysproxy::force_restore_all` 把仍激活的守卫当场复位（直接 ⌘Q 时主循环里的守卫来不及析构）；启动时前端调 `sysproxy_reset_stale`，系统代理开着、指向回环地址且端口无人监听即判为上次残留，关掉并 toast 提示（崩溃 / 强杀连退出事件都没有）。仍建议只在专用机器上跑。
- RPA 依赖一个正在渲染的活动桌面，不是无头，锁屏 / 息屏即失效。
- 同一时刻只能用一个微信号采集；扩容靠多个微信号轮换。
- 只能采公开内容。使用须符合平台规则与法律法规，风险自负。
